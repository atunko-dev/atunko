= CLI Usage
:description: Command reference for atunko CLI

atunko provides a CLI interface for headless and scripted usage of OpenRewrite recipes,
an interactive TUI for browsing and selecting recipes, and a browser-based Web UI.

== Commands

=== `tui` — Interactive recipe browser

Launch the full-screen terminal UI for browsing, searching, and selecting recipes.
This is the default command when no subcommand is specified.

[source,bash]
----
atunko tui
atunko        # same as above — tui is the default
----

==== Options

[cols="1,3"]
|===
| Option | Description

| `--project-dir <path>`
| Project directory for recipe execution (default: `.`). Uses the Gradle Tooling API to
resolve source dirs, resource dirs, test dirs, and compile classpath for each module.
Mutually exclusive with `--workspace`.

| `--workspace <path>`
| Workspace root — scans for all projects underneath and lets recipes run against each
of them. Mutually exclusive with `--project-dir`.

| `--theme <dark\|light>`
| Select a bundled colour theme (default: `dark`).

| `--css-file <path>`
| Load a custom TCSS theme file. Overrides `--theme` and the XDG default
(`~/.config/atunko/theme.tcss`).

| `--log-file <path>`
| Write TUI debug output to a file (useful for troubleshooting)

| `--recipe-jar <path>`
| Add a user recipe jar to the discovery environment (repeatable). Its recipes join the
catalog classified as user recipes. See <<recipe-sources>>.

| `--recipes-file <path>`
| Add a user recipe YAML file to the discovery environment (repeatable). Its recipes
join the catalog classified as user recipes. See <<user-recipe-yaml>>.
|===

==== Theming

The TUI ships with bundled `dark` and `light` themes and supports user-provided TCSS stylesheets.

Theme resolution order:

. `--css-file <path>` — explicit file path (highest priority)
. `~/.config/atunko/theme.tcss` — XDG config auto-load (if the file exists)
. `--theme <dark|light>` — bundled theme selection
. `dark` — built-in default

[source,bash]
----
atunko tui --theme light
atunko tui --css-file ~/.config/atunko/mytheme.tcss
----

==== Layout

Every screen uses the same frame: a fixed three-row header carrying the screen title and
the tab bar, a filling content region, an optional detail pane, and a two-row footer. The
first footer row is session state (counts, active filters); the second is key hints, with
each key highlighted against its label.

The header tab bar names the screens you can move between — Recipes, Tags, Run — marks the
active one, and shows a live count for each. Sort order is *not* a tab; it appears as
`sort:` in the status row beside `src:` and `fav:`.

`?` opens help on any screen, drawn over the current screen rather than replacing it. The
key that dismisses help also performs its own action, so reading help and pressing `r`
runs the recipes in one press.

NOTE: `j` / `k` are not bound. atunko uses arrow keys, `Tab`, `Enter`, `Esc` and
single-letter mnemonics; there are no vim- or emacs-style bindings.

After `r` or `d`, the execution results view lists the changed files: `↑`/`↓` (or
`j`/`k`) navigates, `Enter` opens the per-file diff, `q`/`Esc` goes back.

==== Composite recipes

Recipes that contain sub-recipes are marked with `▶` in the browser.
Use `→`/`e`/`>` to expand and see their sub-recipes, `←`/`<` to collapse.
In the run dialog, `f` flattens a composite into its individual sub-recipes and `F`
flattens all composites at once.

==== Detail view

`Enter` on a recipe opens the detail view with its full description, tags, options,
and sub-recipes. `Space` toggles the recipe's selection, `?` shows the help overlay,
and `Esc`/`q` goes back to the browser.

[#recipe-options]
==== Recipe options

Many recipes take options (for example a package name to target). Press `o` on a
recipe — in the browser or the run dialog — to open the options editor: `↑`/`↓` (or
`j`/`k`) moves between options, `Enter` edits the highlighted value, and `Esc`/`q`
returns. Configured options are used when the recipe runs, and are included in saved
run configurations.

[#run-configurations]
==== Run configurations

A run configuration captures the selected recipes (and their configured options) as a
portable YAML file, so a curated recipe set can be re-used and shared.

* `S` in the browser prompts for a name and saves the current selection to
  `<project-dir>/atunko/runs/<name>.yml`.
* `L` lists the saved configurations in that directory; `Enter` loads one, replacing
  the current selection; `Esc`/`q` cancels.
* `x` in the run dialog opens the export overlay, which renders the current run as an
  OpenRewrite build-plugin configuration: `g` for Gradle, `m` for Maven, `Tab` toggles
  between a minimal plugin snippet and a full standalone build file, `Esc` closes.

Run configuration files can also be exported from the command line — see
<<config-export>>.

=== `run` — Execute a recipe

Execute an OpenRewrite recipe against a single project directory, or against every
project in a workspace.

[source,bash]
----
# Run a specific recipe against a single project
atunko run -r org.openrewrite.java.RemoveUnusedImports --project-dir .

# Run a Spring Boot migration recipe
atunko run -r org.openrewrite.java.spring.boot3.UpgradeSpringBoot_3_0 --project-dir /path/to/project

# Run against every project found under a workspace root
atunko run -r org.openrewrite.java.RemoveUnusedImports --workspace /path/to/workspace
----

In workspace mode the recipe is executed against each discovered project, and a
per-project summary table (project, change count, status) is printed at the end. If
any project fails, the command exits with a non-zero exit code.

==== Options

[cols="1,3"]
|===
| Option | Description

| `-r`, `--recipe <name>`
| Fully qualified recipe name (required)

| `--project-dir <path>`
| Path to a single project directory (one of `--project-dir` or `--workspace` is
required)

| `--workspace <path>`
| Path to a workspace root — scans for all projects underneath and executes against
each (one of `--project-dir` or `--workspace` is required)

| `--recipe-jar <path>`
| User recipe jar added to the execution environment (repeatable), so user recipes can
be run from the command line. See <<recipe-sources>>.

| `--recipes-file <path>`
| User recipe YAML file added to the execution environment (repeatable). Auto-discovered
config-dir recipe files (see <<user-recipe-yaml>>) are always included.

| `--no-daemon`
| Execute in this process instead of through a daemon, starting and contacting none
(see <<daemon>>)

| `--git-checkpoint`
| Create a git stash-based safety checkpoint of the working tree before applying
changes (see <<git-checkpoint>>)

| `--help`
| Show help for the run command
|===

[#git-checkpoint]
==== Git checkpoint

With `--git-checkpoint`, atunko records a safety checkpoint immediately before changes
are applied, so a recipe run can be undone:

[source,bash]
----
atunko run -r org.openrewrite.java.RemoveUnusedImports --project-dir . --git-checkpoint
----

----
Git checkpoint created: 4f0c9a1e...
Restore with: git restore --source=4f0c9a1e... -- .
----

The checkpoint is created with `git stash create` + `git stash store`, which records a
stash entry in `refs/stash` *without touching the working tree* — your uncommitted
changes stay exactly as they are. The printed `git restore --source=<sha> -- .` command
overwrites the working tree with the snapshot's contents, undoing the recipe's changes.
(A plain `git stash apply` would not undo the run: it merges the pre-run diff onto the
current tree rather than restoring the snapshot.)

The checkpoint snapshots *tracked files only*. When untracked files are present, atunko
prints a warning that they are not covered — recipes can still modify untracked source
files, and no checkpoint can bring those back.

In workspace mode the checkpoint is taken *per project directory*, right before that
project's changes are applied. Workspace projects are frequently independent git
clones, so a single checkpoint at the workspace root could cover none of them; in a
monorepo this simply records one stash entry per changed project.

The flag degrades gracefully — in each of these cases a message is printed and the run
continues without a checkpoint:

* the `git` executable is not on the `PATH`
* the target directory is not inside a git repository
* tracked files are unmodified (nothing a stash could snapshot)
* git itself fails (for example a repository without an initial commit) — reported as
  `Git checkpoint FAILED (<reason>)`, never as a clean tree

[#daemon]
=== `daemon` — Inspect and control the daemons

`atunko run --project-dir` executes through a background daemon that keeps the
project's parsed sources in memory between invocations, so a second run against an
unchanged project skips both the build-system scan and the parse. A daemon is started
automatically the first time it is needed; these commands exist so you can see what is
running and stop it.

[source,bash]
----
atunko daemon status                        # list running daemons
atunko daemon stop                          # stop the daemon for the current directory
atunko daemon stop --project-dir /path/to/p # stop a specific project's daemon
atunko daemon stop --all                    # stop every daemon
----

`status` prints one row per daemon:

----
PID      PORT    IDLE      VERSION          PROJECT
84213    41755   2m        0.1.0-SNAPSHOT   /home/me/projects/myapp
----

See <<daemon-caching>> for how the daemon behaves and how to switch it off.

[#recipe-sources]
== Recipe sources

Every recipe in the catalog is classified by source:

* *Bundled* — recipes shipped with atunko's built-in OpenRewrite recipe modules.
* *User* — recipes you add yourself: via `--recipe-jar <path>` or
  `--recipes-file <path>` (both repeatable) on `list`, `search`, `tui`, and `run`, or
  via auto-discovered recipe YAML files (see <<user-recipe-yaml>>).

The `list` and `search` commands filter by source with `--source <all|bundled|user>`
(default: `all`). In the TUI, the `u` key cycles the same filter
(all → bundled → user → all) and the status bar shows the active filter as `src:`.

Discovery and execution share the same environment: a recipe browsable in the TUI via
`--recipe-jar` is also executable there, and `run --recipe-jar` executes user recipes
from the command line. A `--recipe-jar` path that does not exist is an error — the
command fails with `Recipe jar not found` instead of silently reporting an empty
catalog. A user jar that redeclares a name already present in the bundled catalog does
not reclassify or duplicate the bundled recipe: the name stays classified as bundled.

[source,bash]
----
# Only your own recipes, from a custom recipe jar
atunko list --recipe-jar ~/recipes/my-recipes.jar --source user

# Search bundled recipes only
atunko search "logging" --source bundled

# Browse bundled + user recipes in the TUI
atunko tui --recipe-jar ~/recipes/my-recipes.jar

# Execute a user recipe from the command line
atunko run -r io.example.MyTeamRecipe --recipe-jar ~/recipes/my-recipes.jar --project-dir .
----

[#user-recipe-yaml]
=== User recipe YAML files

Declarative OpenRewrite recipe YAML files can be added to the catalog in two ways:

* Explicitly, with `--recipes-file <path>` (repeatable) on `list`, `search`, `tui`,
  and `run`.
* Automatically: every `*.yml`/`*.yaml` file in the `recipes` directory of the atunko
  config dir (`~/.config/atunko/recipes/`, or `$XDG_CONFIG_HOME/atunko/recipes/` when
  set) is loaded on startup, in filename order.

Recipes from these files are classified as user recipes and behave like any other
recipe — they can be browsed, searched, selected, and executed.

[source,bash]
----
mkdir -p ~/.config/atunko/recipes
cp my-recipes.yml ~/.config/atunko/recipes/   # auto-discovered from now on

atunko list --source user                     # verify they were picked up
atunko search "cleanup" --recipes-file ./team-recipes.yml
----

A file that cannot be loaded (malformed YAML, invalid recipe definition) is skipped
with a warning on stderr — it never blocks startup or hides the rest of the catalog.

[#favorites-and-recent]
== Favorites and recently used

The TUI remembers which recipes you care about and which you ran last, across sessions.
Both are stored as plain YAML files in the atunko config dir (`~/.config/atunko/`, or
`$XDG_CONFIG_HOME/atunko/` when set).

=== Favorites

In the browser, press `f` to toggle the highlighted recipe as a favorite — favorites
are marked with `*` after their name. Press `F` to cycle the favorites filter
(all → favorites only); the active filter is shown as `fav:` in the status bar.

Favorites persist in `favorites.yml` (a plain list of recipe names) and every toggle is
saved immediately. A missing or malformed file simply reads as "no favorites" — it
never blocks startup.

=== Recently used

Every recipe execution from the TUI is recorded in `recent.yml`, newest first, with an
ISO-8601 timestamp. Re-running a recipe moves it to the front; the list is capped at
20 entries.

The `s` key cycles the sort order name → tags → recent. With the `recent` sort order,
recently executed recipes appear first (newest first) and everything else follows in
name order.

NOTE: `list` and `search` also accept `--sort recent` for parity, but without a TUI
session's recent context it currently falls back to name order.

== Performance — LST caching

Parsing dominates recipe-execution cost, so atunko avoids re-parsing whenever it can.
There are two mechanisms, one for long-lived sessions and one for the command line.

=== In-process cache (TUI and Web UI)

Long-lived sessions keep the parsed sources (OpenRewrite LSTs) of each project in an
in-memory cache, so repeated executions against the same project reuse the parsed
sources instead of re-parsing from scratch.

The cache invalidates itself automatically: before each execution the project's source
and resource directories plus its build files are fingerprinted (file size, modification
time, and a content checksum), and classpath entries such as dependency jars are
fingerprinted by size and modification time. Any difference — a modified, added, or
removed file, a rebuilt dependency, or a project re-scan that changes the classpath or
source directories — discards the cached entry and re-parses the whole project.

The cache is per-session and in-memory only; nothing is written to disk, and cached
entries are released automatically under memory pressure.

To disable it, set the system property `atunko.lst.cache.disabled=true`:

[source,bash]
----
java -Datunko.lst.cache.disabled=true -jar atunko.jar tui
----

[#daemon-caching]
=== Daemon (CLI)

`atunko run` exits after every invocation, so an in-process cache cannot help it. Instead
the run is executed by a long-lived daemon that holds the parsed sources between
invocations. The first run pays the usual parse cost; subsequent runs against an
unchanged project skip it.

LSTs are never written to disk — OpenRewrite trees cannot be serialized — so keeping
them alive in a process is the only way to reuse them across runs.

How it behaves:

* **One daemon per project root**, started automatically when `atunko run --project-dir`
  needs one. The first auto-start prints a one-line notice naming the daemon and how to
  stop it.
* **At most three daemons** are kept. Starting a fourth stops the least recently used
  idle one; a daemon currently serving a request is never stopped.
* **Idle daemons exit after 30 minutes**, releasing the memory their cached trees held.
* **Invalidation** works exactly as for the in-process cache: the project's `.java`
  files are fingerprinted before each run, and any change re-parses the project.
* **A daemon is never reused across atunko versions.** A daemon started by a different
  version is stopped and replaced, so trees parsed by another OpenRewrite are never
  served.
* **Failures are never fatal.** If a daemon cannot be started or reached, the reason is
  printed as a warning and the run continues in this process with the same result.

Runs that pass `--recipe-jar` or `--recipes-file` always execute in-process: the daemon
builds its recipe environment from its own classpath and would not see those recipes.
Workspace runs (`--workspace`) also execute in-process.

==== Switching it off

[source,bash]
----
atunko run -r <recipe> --project-dir . --no-daemon      # this run only
java -Datunko.daemon.disabled=true -jar atunko.jar run ...   # every run
----

==== Configuration

[cols="1,3"]
|===
| System property | Description

| `atunko.daemon.disabled`
| `true` disables the daemon entirely — no daemon is started or contacted

| `atunko.daemon.idle-timeout`
| How long an idle daemon lives, as seconds or an ISO-8601 duration (default: `PT30M`)

| `atunko.daemon.max`
| How many daemons are retained before the least recently used idle one is stopped
(default: `3`)

| `atunko.daemon.max-heap`
| Maximum heap for each daemon process, in `-Xmx` syntax (e.g. `1g`). Unset leaves the
daemon on JVM defaults, which allow it a quarter of physical memory — set a bound where
several daemons share a machine with memory-hungry builds, such as CI

| `atunko.daemon.registry.dir`
| Where daemon registry files live (default: `$XDG_STATE_HOME/atunko/daemons`, falling
back to `~/.local/state/atunko/daemons`)
|===

==== Security

The daemon listens on the loopback interface only, on an ephemeral port, and every
request must present a per-daemon random token. The token is stored in the daemon's
registry file, which is created with owner-only permissions. Loopback alone is not an
access boundary on a shared machine — any local user can connect to `127.0.0.1` — which
is why the token exists.

Each daemon also writes a log file beside its registry entry; that is where to look if a
daemon fails to start.

== Running via Gradle

During development, commands can be run via Gradle:

[source,bash]
----
./gradlew :atunko-cli:run                           # Launch TUI (default)
./gradlew :atunko-cli:run --args="list"             # List all recipes
./gradlew :atunko-cli:run --args="search 'spring'"  # Search recipes
./gradlew :atunko-cli:run --args="run -r org.openrewrite.java.RemoveUnusedImports --project-dir ."
----
