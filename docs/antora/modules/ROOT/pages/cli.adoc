= CLI Usage
:description: Command reference for atunko CLI

atunko provides a CLI interface for headless and scripted usage of OpenRewrite recipes,
plus an interactive TUI for browsing and selecting recipes.

== Commands

=== `tui` — Interactive recipe browser

Launch the full-screen terminal UI for browsing, searching, and selecting recipes.
This is the default command when no subcommand is specified.

[source,bash]
----
atunko tui
atunko        # same as above — tui is the default
----

==== Options

[cols="1,3"]
|===
| Option | Description

| `--project-dir <path>`
| Project directory for recipe execution (default: `.`). Uses the Gradle Tooling API to
resolve source dirs, resource dirs, test dirs, and compile classpath for each module.

| `--theme <dark\|light>`
| Select a bundled colour theme (default: `dark`).

| `--css-file <path>`
| Load a custom TCSS theme file. Overrides `--theme` and the XDG default
(`~/.config/atunko/theme.tcss`).

| `--log-file <path>`
| Write TUI debug output to a file (useful for troubleshooting)

| `--recipe-jar <path>`
| Add a user recipe jar to the discovery environment (repeatable). Its recipes join the
catalog classified as user recipes. See <<recipe-sources>>.

| `--recipes-file <path>`
| Add a user recipe YAML file to the discovery environment (repeatable). Its recipes
join the catalog classified as user recipes. See <<user-recipe-yaml>>.
|===

==== Theming

The TUI ships with bundled `dark` and `light` themes and supports user-provided TCSS stylesheets.

Theme resolution order:

. `--css-file <path>` — explicit file path (highest priority)
. `~/.config/atunko/theme.tcss` — XDG config auto-load (if the file exists)
. `--theme <dark|light>` — bundled theme selection
. `dark` — built-in default

[source,bash]
----
atunko tui --theme light
atunko tui --css-file ~/.config/atunko/mytheme.tcss
----

==== Browser key bindings

[cols="1,3"]
|===
| Key | Action

| `↑` / `↓`
| Navigate recipe list

| `Enter`
| Open recipe detail view

| `Space`
| Toggle recipe selection

| `a`
| Cycle selection (none → all → none)

| `r`
| Open run dialog with selected recipes

| `t`
| Open tag browser

| `/`
| Enter search mode (type query, `Enter` to apply, `Esc` to cancel)

| `→` / `e`
| Expand composite recipe (show sub-recipes)

| `←` / `c`
| Collapse composite recipe

| `s`
| Cycle sort order (name → tags → recent). See <<favorites-and-recent>>.

| `u`
| Cycle recipe source filter (all → bundled → user). The active filter is shown as
`src:` in the status bar. See <<recipe-sources>>.

| `f`
| Toggle favorite for the highlighted recipe (marked with `*`). See
<<favorites-and-recent>>.

| `F`
| Cycle favorites filter (all → favorites only). The active filter is shown as `fav:`
in the status bar. See <<favorites-and-recent>>.

| `Esc`
| Clear search, tag, and recipe source filters (reset to full list)

| `q`
| Quit
|===

==== Run dialog key bindings

The run dialog opens when you press `r` from the browser with selected recipes.

[cols="1,3"]
|===
| Key | Action

| `↑` / `↓`
| Navigate run list

| `Space` / `Enter`
| Toggle individual recipe on/off

| `a`
| Cycle selection (all/none)

| `+` / `-`
| Reorder recipes (move highlighted recipe up/down)

| `→` / `e`
| Expand composite recipe

| `←` / `c`
| Collapse composite recipe

| `f`
| Flatten composite (replace with individual sub-recipes)

| `r`
| Run selected recipes (apply changes)

| `d`
| Dry-run (preview changes without applying)

| `Esc` / `q`
| Back to browser
|===

==== Composite recipes

Recipes that contain sub-recipes are marked with `▶` in the browser.
Use `→`/`e` to expand and see their sub-recipes, `←`/`c` to collapse.
In the run dialog, `f` flattens a composite into its individual sub-recipes.

=== `list` — List all recipes

List all available OpenRewrite recipes.

[source,bash]
----
# List all recipes
atunko list

# List sorted by tags in table format
atunko list --sort tags --format table
----

==== Options

[cols="1,3"]
|===
| Option | Description

| `--sort <name\|tags\|recent>`
| Sort order: by recipe name (default) or by tags (`recent` is accepted for parity
with the TUI, see <<favorites-and-recent>>)

| `--format <text\|table>`
| Output format: plain text (default) or table

| `--source <all\|bundled\|user>`
| Filter by recipe source: bundled recipes, user recipes, or both (default: `all`).
See <<recipe-sources>>.

| `--recipe-jar <path>`
| Add a user recipe jar to the discovery environment (repeatable). Its recipes are
classified as user recipes. See <<recipe-sources>>.

| `--recipes-file <path>`
| Add a user recipe YAML file to the discovery environment (repeatable). Its recipes
are classified as user recipes. See <<user-recipe-yaml>>.

| `--help`
| Show help for the list command
|===

=== `search` — Search recipes

Search for OpenRewrite recipes matching a keyword.

[source,bash]
----
# Search for recipes matching a keyword
atunko search "spring boot"
atunko search "unused imports"

# Search in a specific field
atunko search "spring" --field name --format table
----

==== Options

[cols="1,3"]
|===
| Option | Description

| `<query>`
| Search keyword (matches against name, description, and tags by default)

| `--field <name\|description\|tags\|all>`
| Restrict search to a specific field (default: all)

| `--sort <name\|tags\|recent>`
| Sort order: by recipe name (default) or by tags (`recent` is accepted for parity
with the TUI, see <<favorites-and-recent>>)

| `--format <text\|table>`
| Output format: plain text (default) or table

| `--source <all\|bundled\|user>`
| Filter by recipe source: bundled recipes, user recipes, or both (default: `all`).
See <<recipe-sources>>.

| `--recipe-jar <path>`
| Add a user recipe jar to the discovery environment (repeatable). Its recipes are
classified as user recipes. See <<recipe-sources>>.

| `--recipes-file <path>`
| Add a user recipe YAML file to the discovery environment (repeatable). Its recipes
are classified as user recipes. See <<user-recipe-yaml>>.

| `--help`
| Show help for the search command
|===

=== `run` — Execute a recipe

Execute an OpenRewrite recipe against a project directory.

[source,bash]
----
# Run a specific recipe
atunko run -r org.openrewrite.java.RemoveUnusedImports --project-dir .

# Run a Spring Boot migration recipe
atunko run -r org.openrewrite.java.spring.boot3.UpgradeSpringBoot_3_0 --project-dir /path/to/project
----

==== Options

[cols="1,3"]
|===
| Option | Description

| `-r`, `--recipe <name>`
| Fully qualified recipe name (required)

| `--project-dir <path>`
| Path to the project directory (required)

| `--recipe-jar <path>`
| User recipe jar added to the execution environment (repeatable), so user recipes can
be run from the command line. See <<recipe-sources>>.

| `--recipes-file <path>`
| User recipe YAML file added to the execution environment (repeatable). Auto-discovered
config-dir recipe files (see <<user-recipe-yaml>>) are always included.

| `--git-checkpoint`
| Create a git stash-based safety checkpoint of the working tree before applying
changes (see <<git-checkpoint>>)

| `--help`
| Show help for the run command
|===

[#git-checkpoint]
==== Git checkpoint

With `--git-checkpoint`, atunko records a safety checkpoint immediately before changes
are applied, so a recipe run can be undone:

[source,bash]
----
atunko run -r org.openrewrite.java.RemoveUnusedImports --project-dir . --git-checkpoint
----

----
Git checkpoint created: 4f0c9a1e...
Restore with: git restore --source=4f0c9a1e... -- .
----

The checkpoint is created with `git stash create` + `git stash store`, which records a
stash entry in `refs/stash` *without touching the working tree* — your uncommitted
changes stay exactly as they are. The printed `git restore --source=<sha> -- .` command
overwrites the working tree with the snapshot's contents, undoing the recipe's changes.
(A plain `git stash apply` would not undo the run: it merges the pre-run diff onto the
current tree rather than restoring the snapshot.)

The checkpoint snapshots *tracked files only*. When untracked files are present, atunko
prints a warning that they are not covered — recipes can still modify untracked source
files, and no checkpoint can bring those back.

In workspace mode the checkpoint is taken *per project directory*, right before that
project's changes are applied. Workspace projects are frequently independent git
clones, so a single checkpoint at the workspace root could cover none of them; in a
monorepo this simply records one stash entry per changed project.

The flag degrades gracefully — in each of these cases a message is printed and the run
continues without a checkpoint:

* the `git` executable is not on the `PATH`
* the target directory is not inside a git repository
* tracked files are unmodified (nothing a stash could snapshot)
* git itself fails (for example a repository without an initial commit) — reported as
  `Git checkpoint FAILED (<reason>)`, never as a clean tree

[#recipe-sources]
== Recipe sources

Every recipe in the catalog is classified by source:

* *Bundled* — recipes shipped with atunko's built-in OpenRewrite recipe modules.
* *User* — recipes you add yourself: via `--recipe-jar <path>` or
  `--recipes-file <path>` (both repeatable) on `list`, `search`, `tui`, and `run`, or
  via auto-discovered recipe YAML files (see <<user-recipe-yaml>>).

The `list` and `search` commands filter by source with `--source <all|bundled|user>`
(default: `all`). In the TUI, the `u` key cycles the same filter
(all → bundled → user → all) and the status bar shows the active filter as `src:`.

Discovery and execution share the same environment: a recipe browsable in the TUI via
`--recipe-jar` is also executable there, and `run --recipe-jar` executes user recipes
from the command line. A `--recipe-jar` path that does not exist is an error — the
command fails with `Recipe jar not found` instead of silently reporting an empty
catalog. A user jar that redeclares a name already present in the bundled catalog does
not reclassify or duplicate the bundled recipe: the name stays classified as bundled.

[source,bash]
----
# Only your own recipes, from a custom recipe jar
atunko list --recipe-jar ~/recipes/my-recipes.jar --source user

# Search bundled recipes only
atunko search "logging" --source bundled

# Browse bundled + user recipes in the TUI
atunko tui --recipe-jar ~/recipes/my-recipes.jar

# Execute a user recipe from the command line
atunko run -r io.example.MyTeamRecipe --recipe-jar ~/recipes/my-recipes.jar --project-dir .
----

[#user-recipe-yaml]
=== User recipe YAML files

Declarative OpenRewrite recipe YAML files can be added to the catalog in two ways:

* Explicitly, with `--recipes-file <path>` (repeatable) on `list`, `search`, and `tui`.
* Automatically: every `*.yml`/`*.yaml` file in the `recipes` directory of the atunko
  config dir (`~/.config/atunko/recipes/`, or `$XDG_CONFIG_HOME/atunko/recipes/` when
  set) is loaded on startup, in filename order.

Recipes from these files are classified as user recipes and behave like any other
recipe — they can be browsed, searched, selected, and executed.

[source,bash]
----
mkdir -p ~/.config/atunko/recipes
cp my-recipes.yml ~/.config/atunko/recipes/   # auto-discovered from now on

atunko list --source user                     # verify they were picked up
atunko search "cleanup" --recipes-file ./team-recipes.yml
----

A file that cannot be loaded (malformed YAML, invalid recipe definition) is skipped
with a warning on stderr — it never blocks startup or hides the rest of the catalog.

[#favorites-and-recent]
== Favorites and recently used

The TUI remembers which recipes you care about and which you ran last, across sessions.
Both are stored as plain YAML files in the atunko config dir (`~/.config/atunko/`, or
`$XDG_CONFIG_HOME/atunko/` when set).

=== Favorites

In the browser, press `f` to toggle the highlighted recipe as a favorite — favorites
are marked with `*` after their name. Press `F` to cycle the favorites filter
(all → favorites only); the active filter is shown as `fav:` in the status bar.

Favorites persist in `favorites.yml` (a plain list of recipe names) and every toggle is
saved immediately. A missing or malformed file simply reads as "no favorites" — it
never blocks startup.

=== Recently used

Every recipe execution from the TUI is recorded in `recent.yml`, newest first, with an
ISO-8601 timestamp. Re-running a recipe moves it to the front; the list is capped at
20 entries.

The `s` key cycles the sort order name → tags → recent. With the `recent` sort order,
recently executed recipes appear first (newest first) and everything else follows in
name order.

NOTE: `list` and `search` also accept `--sort recent` for parity, but without a TUI
session's recent context it currently falls back to name order.

== Performance — LST caching

Long-lived sessions (the TUI and the Web UI) keep the parsed sources (OpenRewrite LSTs)
of each project in an in-memory cache. Parsing dominates recipe-execution cost, so
repeated executions against the same project reuse the parsed sources instead of
re-parsing from scratch.

The cache invalidates itself automatically: before each execution the project's source
and resource directories plus its build files are fingerprinted (file size, modification
time, and a content checksum), and classpath entries such as dependency jars are
fingerprinted by size and modification time. Any difference — a modified, added, or
removed file, a rebuilt dependency, or a project re-scan that changes the classpath or
source directories — discards the cached entry and re-parses the whole project.

The cache is per-session and in-memory only; nothing is written to disk, cached entries
are released automatically under memory pressure, and one-shot CLI runs are unaffected.

To disable caching entirely, set the system property `atunko.lst.cache.disabled=true`:

[source,bash]
----
java -Datunko.lst.cache.disabled=true -jar atunko.jar tui
----

== Running via Gradle

During development, commands can be run via Gradle:

[source,bash]
----
./gradlew :atunko-cli:run                           # Launch TUI (default)
./gradlew :atunko-cli:run --args="list"             # List all recipes
./gradlew :atunko-cli:run --args="search 'spring'"  # Search recipes
./gradlew :atunko-cli:run --args="run -r org.openrewrite.java.RemoveUnusedImports --project-dir ."
----
